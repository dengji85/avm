# 订阅女优 / 影片系列 · 新片提醒实现方案

> **状态**：方案定稿（2026-11-20），尚未实施。落地进度以 `CHANGELOG.md` 为准；文中代码位置基于定稿时的快照，行号可能随改动漂移。
>
> 本文记录「订阅新片」为什么这样设计、数据与接口如何约定、哪些能力刻意不做。开源调研结论只保留与决策相关的部分。

---

## 1. 目标与边界

### 1.1 要解决的体验问题

现在用户只能「知道番号再去刮」，没法「等新片自己出现」。已有 `actresses.followed` 只是收藏标记，不会检测新作；影片系列更是完全没有入口。

| 问题 | 用户感受 |
|---|---|
| 关注了女优，但新片发布不知道 | 要自己定期去站点翻演员页 |
| 系列出了续作，库里有前作也不会提示 | 只能靠记忆或偶然刷到 |
| 新片没有可播来源时只能干看着 | 提醒和「去哪看/去哪下」是断开的 |
| 提醒太多、太杂 | 看过的、不想看的、太老的都推，最后关掉通知 |

### 1.2 明确不做

| 不做 | 理由 |
|---|---|
| 内置磁力站清单、代抓磁力、自动下载 | 与项目既有边界一致（见 `docs/浏览器插件与在线资源设计.md` 第 15.1 节）。本期「下载」只做跳转资源页 / 复制番号 / 复制链接 |
| 用户自定义规则表达式（JS / 正则执行环境） | 规则只从白名单枚举里选，参数化匹配；执行用户代码既不可控也不可解释 |
| 把订阅状态写进 `movies` 冗余列 | 订阅是独立域，统计、去重、筛选口径不能被它污染 |
| 为订阅单独再做一套通知体系 | P2 建统一事件出口，订阅只是事件来源之一 |
| 自动把发现的新片全部建成在线记录 | 默认只进提醒列表，用户点「入库」才落库；避免一订阅就灌进几百条虚拟记录 |
| 依赖无头浏览器才能工作 | NAS 上不一定有 Playwright；浏览器只作为可选兜底，关闭后链路必须完整 |

## 2. 开源调研结论

结论：**没有可直接嵌入的开源「JAV 女优订阅 + 新片提醒」服务**。

| 项目 | 许可 | 能提供什么 | 结论 |
|---|---|---|---|
| Whisparr | GPL-3.0 | Radarr/Sonarr 的成人分支：监控清单 → 索引器 → 下载器 → 导入；Docker/NAS/Windows | 只能作为**外部可选服务**对接，代码不能并入本项目 |
| Prowlarr | GPL-3.0 | 索引器聚合，Torznab 搜索 API | 未来磁力适配器的候选实现，不带订阅能力 |
| Stash / stash-box | AGPL-3.0 | 场景/演员元数据、外部 ID、GraphQL | 只能补元数据，无自动监控 |
| Sonarr / Radarr | GPL-3.0 | `monitored / wanted / release` 模型成熟 | 模型可借鉴，业务域不匹配 |
| JavSP / MetaTube / AMMDS | GPL / 混合 | 按番号抓元数据 | 只解决「已知番号补全」，不解决「发现新番号」 |
| JAV-JHS / JavDB Power Tools | MIT | 浏览器插件式「演员订阅 + 新作检测 + 通知」 | 交互与判定可借鉴；依赖浏览器页面，无法承担 NAS 端定时任务 |

关键判断：*arr 系列的「监控」是把条目交给索引器，**它本身不判断女优/系列有没有新片**。JAV 的新片信息在站点演员页、系列页上，这部分没有成熟开源实现，只能自建站点适配。

### 2.1 复用策略：能开源就不自研

复用优先级从高到低：

1. **标准协议对接现成开源服务**：资源搜索走 Torznab/Newznab（Prowlarr / Jackett），下载编排走 Whisparr，元数据走 MetaTube（已集成）。不自研站点爬虫。
2. **复用本仓库已有能力**：provider 框架、HTTP/代理/出站策略、线程池、`source_renew_job` 状态契约、`ingest`、`movie_sources`。
3. **GPL / AGPL 只对接、只借鉴设计**，不复制代码进 MIT 主体。
4. **只有领域特有、且没有标准协议的部分才自建**：演员页/系列页的列表解析、订阅规则判定。

| 需求 | 复用什么 | 方式 | 本期 |
|---|---|---|---|
| 列表采集 | 现有 `providers/` + `http_html` / `http_json` | 扩展可选 `list_works()` | P1 |
| 磁力搜索 | Prowlarr / Jackett（Torznab） | 外部服务 + 标准 API | P3 |
| 下载编排 | Whisparr / qBittorrent | 外部服务，只交付链接或任务 | P3 |
| 元数据补全 | MetaTube / 现有刮削链 | 复用已有能力 | P2 |
| 定时调度 | 现有 daemon + job 模块 | 复用，不引入 APScheduler / Celery | P1 |
| 通知 | 标准 Webhook JSON | 通用出口，不绑定厂商 SDK | P2 |
| 规则判定 | 自建白名单枚举 | 领域专用，无合适通用库 | P1 |

**明确不引入**：APScheduler / Celery / Redis（现有线程模型够用，多一个 broker 只增加 NAS 部署负担）、ORM（项目直写 SQL）、第三方规则引擎（规则类型固定且必须可解释）、全文检索引擎（首版数据量不需要）。

「能用开源」的边界要说清：开源解决的是**搜索 / 下载 / 元数据**这些通用能力，不解决「JAV 演员页新片发现」这个领域问题。后者自建，但接口按标准协议留口，未来可整体替换。

## 4. 总体架构

```
订阅目标（女优/系列）
      │
      ▼
定时扫描（daemon 定时器 + 长任务）
      │  站点适配：javbus / javdb / manual
      ▼
发现表（全量落库，番号去重）
      │
      ├─ 一级规则：日期、番号、关键词、已入库、已看
      ├─ 二级规则：厂牌、标签、系列（需详情补全）
      ▼
提醒中心（站内未读 / Webhook）
      │
      ├─ 在线观看：复用 movie_sources + ingest
      └─ 资源跳转：link provider（未来可插磁力 provider）
```

设计原则：

1. **发现与判定分离**：扫描只负责「看见」，规则在读取与推送时求值。改规则立即生效，不需要重扫，也能解释「为什么没提醒」。
2. **两级过滤**：一级只用列表页已有字段，避免为每条候选抓详情；二级只对通过一级的条目补厂牌/标签。
3. **订阅域隔离**：规则只影响订阅判定，不改变媒体库筛选、统计与去重口径。
4. **失败降级**：单个站点/单个目标失败只写状态，不中断整批。
5. **列表地址自动纠偏**：女優先搜 `/searchstar/{名字}` 再落到 `/star/{id}`；系列名常带 ●○～ 与「（厂商）」，整串搜会被 JavBus 直接 404，因此按符号切段取最有区分度的关键词搜索，再从命中作品详情页反查 `/series/{id}`，之后固定用系列页（完整作品列表 + 翻页）。纠偏结果落库（`site_id` / `page_url`），后续扫描不再重复解析。

## 5. 数据模型

全部通过 `app/db.py` 的迁移段创建（`CREATE TABLE IF NOT EXISTS` + `PRAGMA table_info` 补列），幂等可重复执行。

### 5.1 订阅目标

```sql
CREATE TABLE IF NOT EXISTS subscription_targets (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    kind          TEXT NOT NULL DEFAULT 'actress',  -- actress / series / studio
    name          TEXT NOT NULL DEFAULT '',
    site          TEXT NOT NULL DEFAULT '',         -- javbus / javdb / manual
    site_id       TEXT NOT NULL DEFAULT '',         -- 站点内 ID，优先用它绑定身份
    page_url      TEXT NOT NULL DEFAULT '',
    cover         TEXT NOT NULL DEFAULT '',
    enabled       INTEGER NOT NULL DEFAULT 1,
    baseline_at   TEXT NOT NULL DEFAULT '',         -- 建立订阅的时间（基线）
    baseline_code TEXT NOT NULL DEFAULT '',         -- 基线时的最新番号（仅用于展示）
    last_scan_at  TEXT NOT NULL DEFAULT '',
    last_status   TEXT NOT NULL DEFAULT '',         -- ok / empty / blocked / error:原因
    etag          TEXT NOT NULL DEFAULT '',         -- 条件请求：未变化时跳过解析
    last_modified TEXT NOT NULL DEFAULT '',
    created_at    TEXT DEFAULT (datetime('now','localtime'))
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_sub_target_site
    ON subscription_targets(kind, site, site_id) WHERE site_id <> '';
CREATE INDEX IF NOT EXISTS idx_sub_target_kind ON subscription_targets(kind, enabled);
```

身份规则：**优先 `site + site_id`**；`manual` 类型允许没有 `site_id`，用 `kind + name` 去重。女优同名/改名靠 `site_id` 区分，名称只用于展示。

### 5.2 发现记录

```sql
CREATE TABLE IF NOT EXISTS subscription_findings (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    code         TEXT NOT NULL DEFAULT '',   -- 展示番号
    code_norm    TEXT NOT NULL DEFAULT '',   -- 归一化番号，与 movies.code_norm 同口径
    title        TEXT NOT NULL DEFAULT '',
    release_date TEXT NOT NULL DEFAULT '',
    cover        TEXT NOT NULL DEFAULT '',
    page_url     TEXT NOT NULL DEFAULT '',
    site         TEXT NOT NULL DEFAULT '',
    site_id      TEXT NOT NULL DEFAULT '',
    meta_json    TEXT NOT NULL DEFAULT '',   -- 厂牌/标签/女优快照，供二级规则，不建关联表
    status       TEXT NOT NULL DEFAULT 'new',-- new / read / ignored / archived
    confirm_count INTEGER NOT NULL DEFAULT 2, -- 被扫到几次；新条目从 1 起，第 2 次才算确认
    first_seen_at TEXT DEFAULT (datetime('now','localtime')),
    read_at      TEXT NOT NULL DEFAULT '',
    ignored_at   TEXT NOT NULL DEFAULT ''
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_sub_finding_code ON subscription_findings(code_norm);
CREATE INDEX IF NOT EXISTS idx_sub_finding_date ON subscription_findings(release_date DESC);
CREATE INDEX IF NOT EXISTS idx_sub_finding_seen ON subscription_findings(first_seen_at DESC);
```

一条番号只存一行，**不按目标重复存**，否则同一部片会被多个订阅提醒多次、忽略状态也会打架。

### 5.3 发现与目标的归属

```sql
CREATE TABLE IF NOT EXISTS subscription_finding_targets (
    finding_id INTEGER NOT NULL REFERENCES subscription_findings(id) ON DELETE CASCADE,
    target_id  INTEGER NOT NULL REFERENCES subscription_targets(id) ON DELETE CASCADE,
    first_seen_at TEXT DEFAULT (datetime('now','localtime')),
    PRIMARY KEY (finding_id, target_id)
);
CREATE INDEX IF NOT EXISTS idx_sub_ft_target ON subscription_finding_targets(target_id);
```

同一部片命中「女优 A」和「系列 S」时，提醒卡片合并为一条，展示多个来源标签。

### 5.4 系列别名

```sql
CREATE TABLE IF NOT EXISTS subscription_series_alias (
    site       TEXT NOT NULL DEFAULT '',
    name_norm  TEXT NOT NULL DEFAULT '',   -- 名称去掉 ●○～ 等装饰符、括号与空白后小写
    site_id    TEXT NOT NULL DEFAULT '',
    page_url   TEXT NOT NULL DEFAULT '',
    updated_at TEXT DEFAULT (datetime('now','localtime')),
    PRIMARY KEY (site, name_norm)
);
```

系列名写法一变（`●` / `～` / 全角半角）就会搜不到。第一次通过 `_resolve_series` 纠偏出
`/series/<id>` 后记下这条映射，后续扫描直接命中，不再逐次切词搜索；换名也不会互串，
因为主键是「站点 + 去装饰符后的名字」。

### 5.5 规则

```sql
CREATE TABLE IF NOT EXISTS subscription_rules (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    target_id  INTEGER REFERENCES subscription_targets(id) ON DELETE CASCADE, -- NULL=全局
    rule_type  TEXT NOT NULL,
    op         TEXT NOT NULL DEFAULT 'exclude',  -- exclude / include
    value      TEXT NOT NULL DEFAULT '',
    enabled    INTEGER NOT NULL DEFAULT 1,
    created_at TEXT DEFAULT (datetime('now','localtime'))
);
CREATE INDEX IF NOT EXISTS idx_sub_rule_target ON subscription_rules(target_id);
```

合并语义：**同 `rule_type` 时目标规则覆盖全局规则**（不做叠加），避免「全局允许、目标排除」变成谁也说不清。不同 `rule_type` 之间是「与」。

### 5.5 与 `movies` 的关系

发现表**不存 `movie_id`**。是否已入库、是否已看，全部在查询时按 `code_norm` 与 `movies` / `watch_progress` 做 `LEFT JOIN` 实时派生。原因：影片可能在提醒之后才入库、才看完，存快照必然过期。

`code_norm` 复用现有归一化口径（`app/db.py` 已有 `idx_movies_codenorm`）。

### 5.6 订阅域状态（键值）

```sql
CREATE TABLE IF NOT EXISTS subscription_state (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL DEFAULT ''
);
```

当前只存 `findings_last_seen_at`（进入新片列表的时刻），给顶部未读角标用：`unread-count` 只统计 `status='new'` 且 `first_seen_at` 晚于该时刻的条目，所以「点进去看过」角标即清零。

单条的已读 / 未读是另一回事：`read` / `new` 由用户自己切换（`mark_read` / `mark_unread`），不参与角标计算，避免「看过列表 = 全部已读」把想回看的条目一起吞掉。

## 6. 规则引擎

### 6.1 规则类型

| `rule_type` | `op` | `value` 示例 | 判定 | 数据阶段 |
|---|---|---|---|---|
| `release_after` | include | `2025-01-01` | 发行日期 ≥ 该日 | 一级 |
| `release_before` | include | `2024-12-31` | 发行日期 ≤ 该日 | 一级 |
| `recent_days` | include | `180` | 发行日期在最近 N 天内 | 一级 |
| `exclude_code` | exclude | `ABC-123\nDEF-456` | 番号（归一化后）命中列表 | 一级 |
| `code_regex` | exclude | `^FC2-` | 归一化番号匹配正则（长度上限 + 超时保护） | 一级 |
| `keyword` | exclude | `合集\n总集篇` | 标题包含任一关键词 | 一级 |
| `exclude_actress` | exclude | `名字或站点ID` | 女优名/ID 命中 | 一级（列表页有女优时） |
| `exclude_series` | exclude | `名字或站点ID` | 系列命中 | 二级 |
| `exclude_studio` | exclude | `名字` | 厂牌命中 | 二级 |
| `exclude_tag` | exclude | `标签名` | 标签命中 | 二级 |
| `only_studio` | include | `名字` | 只保留指定厂牌 | 二级 |
| `only_tag` | include | `标签名` | 只保留指定标签 | 二级 |
| `exclude_in_library` | exclude | `1` | 库内已有同 `code_norm` 的影片 | 一级（DB） |
| `exclude_watched` | exclude | `1` | 同番号影片已看完 | 一级（DB） |
| `exclude_ignored` | exclude | `1` | 该番号曾被用户忽略 | 一级（DB） |
| `exclude_co_star` | exclude | `1` | 元信息里出现 ≥2 位已订阅女优（共演 / 合集） | 一级（读时求值） |

**面向用户的呈现（过滤偏好）**：前端不暴露 `rule_type` / `value` 术语，只给收藏者看得懂的选项，映射如下：

| 面板项 | 落库规则 |
|---|---|
| 跳过已看过的 | `exclude_watched` = `1` / `0` |
| 跳过已忽略的 | `exclude_ignored` = `1` / `0` |
| 只看最近 N 天（`0` = 不限） | `recent_days` = `N` |
| 标题含这些词就不提醒 | `keyword`，多值换行拼接 |
| 不想看这些女优 | `exclude_actress`，多值换行拼接 |
| 高级规则（折叠区） | `exclude_code` / `code_regex` / `release_after` / `release_before` / `exclude_co_star` |

- 首次产生订阅时写入默认全局偏好：`exclude_watched`、`exclude_ignored`（值 `1`）。只在全局规则为空时写一次，之后用户改不改都不覆盖。
- 「已入库不提醒」不做成可配项：扫描阶段已跳过库内番号，始终生效。
- 单目标覆盖全局时允许写空值（`keyword` / `exclude_actress` / `exclude_code`），表示「这一项不限制」，用于覆盖全局的同类型排除；`recent_days = 0` 同理表示「不限」。
- 「恢复跟随全局」= 删除该目标下的全部独立规则，重新继承全局。

**入口与交互**

- 「过滤」页管理全局偏好；单个女优/系列的例外从「订阅目标」行的「偏好」进入，页头标注「仅对 XX 生效」，可一键返回全局。
- 新片卡片提供「不想看」菜单：忽略本条、屏蔽该女优、屏蔽标题关键词。卡片上的屏蔽直接写入全局，符合「看到垃圾就屏蔽」的使用习惯。
- 所有偏好改动即时保存，不再整页重载；页头只闪一个「已保存」，预览统计 500ms 防抖刷新。
- 范围与覆盖只在需要时出现，默认界面不暴露全局/目标概念。



### 6.2 求值顺序

1. **基线**（不是规则）：`release_date` 早于 `baseline_at` 的不进入提醒，但可标记为「历史」。从库里订阅时基线取**库内该目标最新作品的发行日**（先补齐库里缺的作品，之后继续提醒新片）；库里没有作品或其他入口建订阅时取订阅当天。基线可以在订阅目标列表里直接改（每行的「起始日期」），改早后重新扫描即可补进老片。
2. **include 白名单**：目标存在任一 `include` 规则时，必须至少命中一条；没有则默认通过。`recent_days` 的值为 `0` 表示不限，视为通过。
3. **exclude 规则**：全局 + 目标合并后，命中任一即排除。
4. **状态类（内建，不需要规则）**：已入库默认不提醒（`exclude_in_library`，一键入库后立即从新片列表消失）；已看 / 已忽略同样默认不提醒。规则的 `exclude_in_library` 只是同义兜底。
5. 通过 → 进入提醒；未通过 → 在「已过滤」视图可见，并展示具体原因。

**多目标合并**：一条发现只要**有一个**命中目标通过规则，就对用户可见；推送文案列出命中的目标名。

### 6.3 两级过滤

| 级别 | 输入 | 规则 | 是否额外请求 |
|---|---|---|---|
| 一级 | 列表页：番号、标题、发行日期、女优名 | 日期、番号、关键词、女优排除、库内/已看 | 否 |
| 二级 | 详情页：厂牌、系列、标签 | 厂牌/系列/标签/白名单 | 是，可关闭 |

二级只对「一级通过」的条目执行；关闭二级时，依赖详情字段的规则会被标记为「未生效」，而不是静默放行。

### 6.4 未知值策略

日期、厂牌、标签缺失时不默认判定为「排除」，按配置 `unknown_date_policy`（默认 `keep`）处理，并在卡片上标「日期未知」。宁可多一条可解释的提醒，也不静默丢失。

### 6.5 「看过的」判定口径

满足任一即视为已看：

- `movies.watched = 1`
- `watch_progress.finished = 1`
- `watch_progress.duration > 0` 且 `position / duration >= 0.9`

限制：只能识别**库内**看过的记录。用户在外面看过、库里没有的，系统无法知道；这条规则的实际语义是「看完后不再重复提醒」。

### 6.6 「不想再关注」的两种粒度

| 粒度 | 落点 | 生效范围 |
|---|---|---|
| 单条 | `subscription_findings.status = 'ignored'` + `ignored_at` | 该番号永久不再提醒 |
| 规则 | `exclude_code` / 关键词 / 实体排除 | 所有命中该规则的发现 |

两者都只作用于订阅域，不写入媒体库黑名单，也不影响库内筛选。

### 6.7 规则预览（dry-run）

保存规则前，用**现有发现记录**跑一遍：

```
POST /api/subscriptions/rules/preview
→ { "visible": 37, "filtered": 12,
    "reasons": [{"rule": "release_after", "count": 8}, ...],
    "blocked": [{"id": 308, "code": "ROE-573", "title": "…",
                 "release_date": "2026-11-06", "reasons": ["exclude_in_library"]}],
    "unknown": 3 }
```

`blocked` 是被挡条目的前 12 条明细（番号 / 标题 / 日期 / 命中原因），前端在预览下方折叠展示，
让「为什么没提醒」可解释，而不是只看一个总数。

只做本地求值，不触发扫描；若依赖二级字段而 `meta_json` 为空，单独返回 `pending_enrich` 数量，提示「需补全 N 条后才能准确预览」。

### 7.1 能力扩展

在 `app/providers/base.py` 增加**可选**列表能力，不实现该方法的 provider 维持现状：

class Provider:

每个条目至少给出：`code`、`title`、`release_date`、`cover`、`page_url`、`site`、`site_id`。有女优名时一并返回，供一级规则使用。

### 7.2 适配范围

| 目标类型 | 首选 | 兜底 |
|---|---|---|
| 女优 | JavBus 演员页 / JavDB 演员页 | 站点搜索页按名字查 |
| 系列 | JavBus 系列页 / JavDB 系列页 | 手动添加作品页 |
| 厂牌 | 站点片商页 | 暂不做，放 P2 |

已知风险：列表页 DOM 是唯一没验证过的环节。实现第一步必须先用真实请求确认结构；确认不了就退回「手动添加作品页 + 浏览器插件上报」的旁路，不硬啃。

### 7.3 扫描节奏

- 两种模式（`subscription.scan_mode`）：
  - `interval`（默认）：`scan_interval_minutes = 360`，加 `±30` 分钟抖动；
  - `cron`：5 段表达式（`scan_cron`，默认 `0 8 * * *`），按本地时间定点，不加抖动。
    解析与下次时间计算在 `app/cron.py`，只支持 `*` / `*/n` / `a` / `a-b` / `a-b/n` / 逗号列表，
    其余语法直接报错（避免写了不生效）。
- 调度线程每 30 秒问一次 `subscription_schedule.should_run()`，改配置 / 表达式 1 分钟内生效，不用重启。
- 状态落 `data/subscription_schedule.json`（`last_auto_scan_at` / `next_due_at` / 配置指纹）。
  Windows 关机或休眠时没有系统级定时器，靠它判断「是否真的错过」：
  `catch_up_on_start` 开启时，启动后若上次扫描之后本该有触发点已过去，就补扫一次（错过多个点也只补一次）；
  关闭则从启动时刻重新计时。
- 表达式写错时后台直接跳过扫描（不会按错误配置打站点），设置界面保存前会先校验。
- 同一站点串行（保留 2 秒页间间隔），**不同站点并行**（最多 3 组，线程池内跑）；
  单站连续失败 3 次后进入冷却（下次跳过），进度按「已完成目标数」上报。
- 单次扫描上限（默认每目标 100 条、3 页），连续命中 10 条已知番号即停（增量）。
- **历史补抓**（`mode="backfill"`，目标行「补抓历史」）：翻页放宽到 12 页 / 500 条，
  且不看连续命中即停；仍受目标 `baseline_at` 约束（要补更老的片先把起始日期改早）。
- 扫描是可取消长任务，重复点击返回同一任务（见 `app/source_renew_job.py`）。
- `last_status` 用用户可读的结论，而不是内部代号：`新增 N 条`、
  `无新片（已追到旧片）`、`无新片（已到起始日期）`、`未变化（页面未更新）`、
  `补抓：…`、`blocked:…` / `error:…`（后两者前端标红）。
- 归档：已读超过 `archive_read_days`（默认 30 天）的发现，在**全量扫描**结束时自动转
  `status='archived'`；归档不参与日常列表与规则过滤，可在「归档」状态里查看 / 取消。
  本轮归档条数随扫描完成文案一起回报（前端 toast「已归档 N 条」）。
- 二次确认：新发现首次落库 `confirm_count=1`，下一轮扫描仍看到才变 2（封顶 9）。
  未确认的条目照常显示，但不计入未读角标，也不会让「未读」筛选出现站点偶发脏数据；
  **自动探测也跳过未确认条目**（结果计入任务状态 `skipped`，前端文案注明「N 条待确认未检查」）。
- 共演判定：读列表时用发现元信息里的女优，与「已订阅且启用」的女优求交集，
  ≥2 位即在卡片上标「共演」；需要挡掉时可开高级规则 `exclude_co_star`。
- 系列别名：纠偏出 `/series/<id>` 后写入 `subscription_series_alias`，下次扫描直接命中。

### 8.4 在线资源探测（「这个番有没有在线资源」）

用户要的不是磁力，而是**判断值不值得点开**。做法：拿番号去在线站点问「有没有作品页」。

- **站点分类**：`config.online_sites[].kind` 区分 `watch`（在线观看：123av / Jable…）与 `meta`（元数据查询：JavBus / JavDB / JavLibrary / AV-Wiki…）。设置页可改；旧配置按预设 id 自动补 `kind`，自定义站点缺省 `meta`。**探测只用 `watch`**：资料站命中只说明有资料页，对「能不能看」没有参考价值（曾短暂作为弱提示，实测是噪音），已退出探测；它们仍保留在设置里给详情页查元数据。
- **站点来源**：复用 `config.online_sites`（详情页「第三方网站」那一套），只取**按番号直达作品页**的模板（含 `{code}`、且不是搜索型 URL）。搜索页返回 200 说明不了任何问题，一律排除。命中观看站即可定论、少发请求。
- **判据保守**：`200` 且页面**正文出现番号**、并且**标题含番号或页面带播放器特征**（`<video` / `.m3u8` / `hlsurl` / `videojs` 等）才算「有」——只认正文里的番号太松，Chrome 错误页、验证页、站点首页都会回显 URL，会把没有资源的站点误判成有；`404/410` 记「该站没有」，继续问下一站；超时 / 连接失败 / 被墙 / 仍然是验证页记「未知」，**不写结论**，下次探测会重试。
- **错误页不算内容**：Chrome 自身的错误页（`ERR_CONNECTION_TIMED_OUT` 等，正文回显请求 URL）一律当抓取失败（`cdp_fetch.is_error_page`），不参与命中判定。
- **Jable 这类站的取页通道**：直连 requests 会被 Cloudflare 以 403 挡掉（TLS 指纹 + JS 挑战，带 cf_clearance 也不一定过），探测改用**独立的一次性 Chrome**（端口 = `scraper.chrome_debug_port + 1`、profile `data/chrome_probe_profile`、窗口挪到屏幕外、走同一个 `network.proxy` 出口）。实测 headless 会一直被挑战页卡住，**真实浏览器几秒放行**；没有桌面会话（容器 / 纯命令行）时自动退回 headless。取到页面后再按上面的判据确认，因此 Jable 的 404 页不会被当成「有」。
- **单页应用要等落定**：页面刚打开时可能只有空壳（标题还没有番号）。CDP 抓取带 `require` 判定，等到「标题含番号 / 明确 404 / 出现播放器」才收，避免把半成品当结论。
- **反爬通道**：先用直连式请求拿状态码（`404` 只有这一层能拿到），拿到 `403` / 验证页 / 网络失败时，走 `cdp_fetch` 用**探测专用 Chrome**（见上一条，不是刮削那台）重取页面。页面仍是 `detect_blocker` 认出的验证页就保持「未知」，不硬判。
- **验证凭证复用**：CDP 通道验证通过后，用 `cdp_cookies` 取该站点生效的 Cookie 与 UA，存到 `data/site_cookies.json`（按站点 id，含抓取时间）。后续请求直接带上它们，不再重跑浏览器验证；凭证过期被挡时再回落 CDP 刷新一次。资料站/观看站都适用。注意两点：`cf_clearance` 与 UA 绑定，所以 UA 一起存、一起用；像 Jable 这类还校验 TLS 指纹的站点，存了 Cookie 直接请求照样 403，只能每次走 CDP（结论照样落库，默认不重复探测）。
- **单一结论**：只认观看站命中 → `probe_kind='watch'`，前端显示「有在线资源 · 站点名」；资料站不再产生结论。
- **落库**：`subscription_findings.probe_site / probe_status / probe_kind / probe_at`（`''` 未知 / `ok` 有 / `none` 无）；历史「仅有资料页」（`probe_kind='meta'`）的结论在迁移时清空，按新规则重探。
- **节奏**：`subscription_probe_job.py` 后台任务，单次最多 200 条，条间与站间各 1.2 秒，可取消、有百分比；不阻塞请求，不会因为一条失败中断整批。任务状态额外返回 `unknown`（站点不可达 / 被挡）与 `skipped`（`confirm_count < 2` 的待确认条目，非 force 时跳过），完成后文案会把这些条数写清楚。
- **单条重探**：卡片上的「重新探测」调 `POST /api/subscriptions/findings/{id}/probe`，同步只问一条（`delay=0`、`ttl_days=0`），返回最新结论字段；批量任务在跑时也不冲突（各自独立）。
- **自动兜底（延迟检测）**：扫描结束或服务启动后，`schedule_auto()` 用 `threading.Timer` 延迟 `auto_probe_delay_seconds`（默认 180 秒）在长任务池补跑一轮——只补没结论的、跳过已入库的，单轮上限 `auto_probe_batch`（默认 40）。同一时间只排一个定时器，人工任务在跑时直接跳过；可在「订阅新片」顶部设置里用 `auto_probe` 关闭。页面每 15 秒轻量查一次探测状态，发现后台开跑就切快轮询，跑完自动刷新列表显示标记。
- **速度与复用**（原则：能复用就复用，不能复用也要保证可用）：
  - 结论落库，默认只探「没有结论」的发现，已探过的不会重复验证；
  - 验证凭证（Cookie + UA）落 `data/site_cookies.json`，下次直接走普通请求（约 1 秒/条）；
  - 直连被挡（403/503）的站点，本批次后续条目直接走 CDP，不再做必然失败的请求；
  - 被限流（429）的站点，本批次直接跳过（同一出口 IP 换 CDP 也一样被限），冷却 5 分钟后恢复；
  - 没有可复用凭证的站点（如 Jable）仍走 CDP 兜底，单条约 30–40 秒，但每条只验一次。
- **123av**：就是预设里的「123av」，`kind=watch`。实测（经代理）：有作品 `200` 且标题带番号；无作品 `404`——判据不需要站点专属解析。
- **Jable**：`kind=watch`，有 Cloudflare Loader 验证；直连请求拿不到正文，靠上面的 `cdp_fetch` 通道通过（实测 26/27 命中走 Jable）。若某次验证没过，保持「未知」下次重试，不误判成「无资源」。

## 15. 性能设计

性能目标不是「跑得快」，而是**扫描不拖垮服务、列表不随数据量退化、NAS 上不产生额外部署负担**。

### 15.1 扫描：少请求、可增量

- **增量翻页**：从第 1 页开始，遇到连续 N 条已知番号（默认 10）或到达基线即停；单目标最多 3 页 / 100 条。
- **条件请求**：保存 `ETag` / `Last-Modified`，站点返回 304 时直接跳过解析。
- **单站串行** + 页间 1–2 秒随机间隔；跨站并发 ≤2，沿用长任务线程池；每轮设总请求预算。
- **失败退避**：30 分钟 → 2 小时 → 6 小时，成功即重置；连续失败进入冷却。
- **列表优先**：只抓列表；详情仅在二级开启且一级通过时抓，单轮详情数设上限（默认 50）。
- 复用现有 HTTP 会话、代理与出站策略，不新建 HTTP 栈。

### 15.2 写库

- 单轮扫描一个事务，`executemany` 批量 upsert（`ON CONFLICT(code_norm) DO UPDATE`），只更新展示字段。
- 归属表用 `INSERT OR IGNORE`，避免重复写。
- 索引覆盖查询：`code_norm` 唯一、`release_date`、`first_seen_at`。
- 不存冗余状态列，已入库/已看实时派生，避免双写不一致。

### 15.3 规则求值

- **每请求编译一次**规则集，按目标分组；不逐条查规则表。
- 能下推 SQL 的条件先下推：日期区间、`code_norm IN`、`EXISTS movies/watch_progress`；Python 只跑正则、关键词、标签。
- 正则预编译，模式长度上限 200，单条求值设超时保护。
- 结果缓存键 `(rules_updated_at, findings_max_id)`，规则变化或新发现即失效；60 秒 TTL 兜底。
- 列表接口不返回 `meta_json`，只在详情/预览返回。

### 15.4 查询与接口

- **keyset 分页** `(release_date DESC, id DESC)`，禁止大 `OFFSET`。
- 默认 `limit=50`，上限 200。
- 未读计数单独 `COUNT` + 30 秒内存缓存，轮询不触发全表扫描。
- 已入库/已看用 `EXISTS` 子查询，命中 `idx_movies_codenorm`。

### 15.5 前端

- 首屏 30 条 + 触底加载；封面 `loading="lazy"` + 固定比例容器，避免布局抖动。
- 未读轮询 60 秒，页面不可见（`document.hidden`）时暂停。
- 规则 dry-run 输入防抖 300ms。

### 15.6 资源 provider

- 并发查询，单 provider 4 秒、总预算 8 秒；失败不重试，用户手动刷新才重试。
- 内存 LRU 缓存（10 分钟、最多 200 条），键 `(provider, code)`，不落库。
- 搜索结果不参与列表主查询，只在用户点开抽屉时加载。

### 15.7 容量阈值

| 发现量 | 策略 |
|---|---|
| < 5k | 现有索引足够，不引入 FTS |
| 5k–50k | 增加 `(status, release_date)` 复合索引，默认只查最近 180 天 |
| > 50k | 再评估 FTS5 / 归档一年前发现；首版不引入 |

**性能预算**（本机、`limit=50`）：

- 1 万条发现下，列表接口 P95 < 200ms
- 规则预览 1 万条 < 300ms
- 100 个目标的单轮请求数 ≤ 目标数 × 3 页（增量命中即停）
- 扫描期间交互接口不被占满（长任务只走长池）

## 16. 验收

按项目四道闸执行：

1. `python -m compileall -q app`

额外验证：

- 迁移重复执行两次不报错

- 构造 1 万条发现记录，列表接口与规则预览达到第 15.7 节的性能预算
- 同一目标连续扫描两次，第二次因增量与条件请求明显减少请求数

## 17. 风险与未决

| 风险 | 处理 |
|---|---|
| 演员页/系列页结构未验证 | 实现第一步先真实请求确认；不行就走插件上报旁路 |
| 女优同名/改名 | 绑定 `site_id`，名称只做展示 |
| 系列同名不同厂 | 必须用站点 `series_id`，不用名称匹配 |
| 站点限流/封禁 | 串行 + 抖动 + 冷却 + 每目标上限 |
| 提醒噪音 | 基线 + 规则 + 每日上限 + 摘要 |
| 规则误杀 | dry-run 预览 + 已过滤视图可解释 + 一键恢复 |
| 磁力链接失效 | 只做短 TTL 缓存，不落库 |
| 合规 | 不内置磁力站、不代抓、不自动下载；资源由用户配置与选择 |

- 是否把「订阅」入口同时放到发现页和女优详情页（默认只放女优页/系列页 + 独立订阅页）。
- Webhook 的具体 payload 结构，P2 与统一事件出口一起定。
